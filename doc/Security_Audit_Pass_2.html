1   Scope and method

The first review (Security_Audit.eml) looked at v1.0.1, and its follow-ups at v1.0.3 and v1.0.6. Since v1.0.6, about 18,000 lines of src/ changed: dictionaries, shared content, --repair, --compact, --diff-extract, --encrypt-archive, append in place, and Windows. This review covers the whole code again, and these changes in particular.
The review had four parts. Each part read the code, and tried each attack on a build of v1.1.4 as a normal user on Linux:
  1. An archive from an attacker as input: the header, trailer, index and CBOR, the decoders, and the paths that read an archive (-t, --info, --verify, -x, append, compact, repair).
  2. The cryptography: keys, nonces, what each AAD binds, the KDF limits, downgrade and rollback, the change of passphrase, --encrypt-archive, and the passphrase.
  3. Extraction: what -x, --diff, --diff-extract and -n do to the file system with an archive from an attacker, also as root.
  4. The writer and the command line: the walk, temporary and spill files, the rename of the archive, locks, repair, the configuration, the passphrase sources, and the escape of names in each output.
"Tested" means that the review made the attack happen. "Code" means that the review found it in the code. The review reproduced findings 13, 14, 18, 19 and 20 a second time, on a separate build. Tests that need a second account, root, Windows, macOS or a BSD were not run: those parts were reviewed in the code only.
The findings continue the numbers of the first review, so that each number names one finding in both documents.

3   Findings

Finding 13. A directory and a link to . with one path change the destination (high)

Where: finishDir and extractNode in src/​internal/​archive/​extract.​go, and Index.Validate in src/​internal/​format/​index.​go. Tested.
Problem. The index accepts two live members with one path. An archive holds a directory x (mode 0777, its times, user.* attributes, an owner) and a symbolic link x -> ., in either order. Phase 1 makes both, and the link takes the place of the empty directory. The last phase opens x by its path, follows the link, and applies the metadata of the directory to the destination itself. a/x -> .. does the same one level down. The fix of finding 2 removes a member ., but not a member whose path leads to the destination.
Attack. A user runs eictar -xf evil.ect -d ~. The home directory becomes 0777 less the umask, its times and its user.* attributes change, and the run ends with exit 0. With -p, the mode is exactly 0777, or 03777. As root there is no umask, and --preserve-owner gives the destination to the uid that the archive names. With -d / that is /. On a file system that ignores case, X and x are enough, so a check for equal paths is not a full fix.
Evidence. A destination of mode 0700 became 0775, with mtime 1970-01-01 and user.audit="pwned", exit 0. The review reproduced this on a separate build.
Fix. In the last phase, apply metadata only to the directory that phase 1 made or found: record its device and inode, and refuse a link at the last name (Lstat, then compare with the open directory). Never apply metadata to the destination itself. Set the times through the open descriptor. When a directory member meets a link on disk, replace the link (as GNU tar does) or refuse the member. The fix of finding 14 also closes this one.
Status. Fixed after v1.1.4, with the fix of finding 14. A link at the name of a directory member is refused with exit 3, and no directory below the destination can be the destination itself. TestExtractDoesNotChangeTheDestinationThroughALink tests the three archives above, and TestBeneathForgetsAReplacedDirectory tests that a directory that the archive replaces with a link is not used again. The archives of the review give exit 3, and the destination keeps its mode, times and attributes.

Finding 14. Extraction follows a link that another user put inside the destination (medium)

Where: each operation of src/​internal/​archive/​extract.​go through os.Root: fileWorker (OpenRoot), MkdirAll, parent, writeSymlink, applyTimes, extractHardlink and finishDir. Tested.
Problem. os.Root refuses a path that leaves the destination, but it follows a relative link that stays inside it. Design §7.6 says so, and calls the risk small when extraction goes into a new directory. But design §14.3 says "Extraction never follows a link and never goes through a linked directory". That is true only for a link that leads out.
Attack. Root restores /home from a backup. The backup holds alice/.ssh2/authorized_keys, a file of alice with her key. Before the restore, alice runs ln -s ../bob/.ssh ~/.ssh2. The restore writes her file over bob/.ssh/authorized_keys, and gives bob's .ssh the mode of her directory. Alice can then log in as bob. With -d /, the same reaches /root/.ssh and /etc/cron.d. A race does the same with no link before the run: phase 1 makes all the directories, and phase 2 opens them again by path, so alice can swap a new directory under her home for a link.
Evidence. With the planted link, bob's authorized_keys held alice's key, and his .ssh went from 0700 to 0775, exit 0. The review reproduced this on a separate build. The race worked in 3 runs of 3.
Fix. Resolve each member path with no link following: on Linux 5.6 and later, openat2 with RESOLVE_NO_SYMLINKS and RESOLVE_BENEATH; elsewhere, open one name at a time with O_NOFOLLOW and O_DIRECTORY from the destination descriptor, and do the last operation with an *at call. Keep os.Root as a second barrier. Until then, correct design §14.3, and warn against an extraction as root into a tree where other users own directories.
Status. Fixed after v1.1.4. beneath, in src/​internal/​archive/​dest.​go, opens each directory of a path one name at a time through os.Root, refuses a link, and checks that the directory that it opened is the one that it looked at. os.Root stays as the second barrier. This is the walk of the fix above, with os.Root in place of openat2, so it is the same on each system. Design §7.6 and §14.3 now say so. TestExtractDoesNotFollowALinkInTheDestination tests the planted link, and TestBeneathRefusesADirectorySwappedForALink the race. The script of the review refused the swap in 3 runs of 3, and bob's files did not change. A hardlink still links by its paths after a check of both directories, so a swap in that time can move it, but only inside the destination.

Finding 15. A race between the check of -f and its resolution (medium)

Where: createTarget in src/​internal/​archive/​writer.​go (checkLinks, then filepath.EvalSymlinks), and the same order in CompactArchive in src/​internal/​archive/​mutate.​go. Tested.
Problem. checkLinks applies the rule of fs.protected_symlinks to each part of the path. When the path does not exist yet, it finds no link. Then EvalSymlinks resolves the path a second time. A link that appears between the two calls is followed with no check, and the rename replaces its target.
Attack. The attack of finding 4: root runs eictar -cf /tmp/backup.ect from cron. A local user makes and removes the link /tmp/backup.ect -> /etc/passwd in a loop. A failed try gives exit 3 or a normal create, so the user can try at each run.
Evidence. A test with the rule of another user's link, and a goroutine that made and removed the link, replaced the victim file in each of 6 runs, after 2 to 14 creates.
Fix. Resolve the path in one pass: Lstat each part, apply the rule to each link, read it and go on with its target, to at most 40 links. Do not call EvalSymlinks. Then open the parent of the target, and do the open of the old file, the create of the temporary file and the rename relative to that directory descriptor.
Status. Fixed after v1.1.4. resolveArchive, in src/​internal/​archive/​resolve_​other.​go, is the one pass: it reads each name with Lstat, applies the rule to each link, and continues with the target of the link, to at most 40 links. On Unix, create and compact no longer call EvalSymlinks. Then the open of the old file must give the file that Lstat found at the resolved path, or the program stops with exit 3. A link that appears after the pass is not followed: the rename replaces the name. The operations stay by path, not relative to a directory descriptor. A swap of a directory of the path needs write permission on its parent, and gives nothing that the rule does not allow already. Design §9 says why. TestCreateRaceWithAPlantedLink is the test of the review: before the fix it replaced the victim after 5 to 16 tries. Now no try replaces it, in up to 2,000 tries or 2 seconds. TestCreateRefusesAFileSwappedBeforeItsOpen and TestCompactRefusesAFileSwappedBeforeItsOpen test the check of the open.

Finding 16. The check of -f does not look at a link inside the target of a link (medium)

Where: checkLinks in src/​internal/​archive/​writer.​go, used by create, compact, the change of passphrase and --encrypt-archive. Tested.
Problem. checkLinks checks only the parts of the path as the user typed it. When a part is a link that it can follow, it does not check the links in the target of that link. EvalSymlinks follows them all. The kernel applies its rule to each link that it follows.
Attack. Root has its own link ~/backups/latest.ect -> /tmp/latest.ect, and /tmp/latest.ect does not exist. A local user puts the link /tmp/latest.ect -> /etc/shadow. Then eictar -cf ~/backups/latest.ect by root replaces /etc/shadow. No race is necessary.
Evidence. -f on the planted link was refused; -f on the user's own link to the planted link replaced the victim file. The review confirmed the gap in the code.
Fix. The one-pass resolution of finding 15, which applies the rule to every link that it follows, also inside a link target.
Status. Fixed after v1.1.4, with the fix of finding 15. TestCreateChecksALinkInsideALinkTarget and TestCompactChecksALinkInsideALinkTarget test the two links of the attack. The create and the compact stop with exit 3, and the victim stays.

Finding 17. Create gives the new archive the mode of a file that another user put at -f (medium)

Where: createTarget and createTemp in src/​internal/​archive/​writer.​go. Tested (the mode); Code (the owner).
Problem. The new archive takes the permission bits of the file that it replaces, and the umask does not limit them. The owner of that file is not checked.
Attack. A local user creates /tmp/backup.ect with mode 0666 before root's eictar -cf /tmp/backup.ect. Root can rename over the file of another user. The new archive, owned by root, has mode 0666: the user can read a plaintext backup, and change or cut any backup. Under fs.protected_regular, tar gets EACCES for this file. In a shared group directory, the same lets one member widen the archive of another.
Evidence. A file of mode 0666 at -f, then umask 077 and a create: the archive had mode 0666.
Fix. Take the mode only from a file that the caller owns. In a sticky directory that everyone can write, refuse a file that neither the caller nor the owner of the directory owns (exit 3), as the kernel does. In other cases, use 0666 less the umask.
Status. Fixed after v1.1.4. The caller's own file gives its mode, as before. In a sticky directory that everyone can write, a file that neither the caller nor the owner of the directory owns is refused with exit 3. Any other file of another user gives 0666 less the umask, with no bit that the old file does not have. This keeps root's archive in the home of a user from a mode wider than the old one. TestCreateDoesNotTakeTheModeOfAnotherUsersFile tests the mode, and TestReplaceRule the rule.

Finding 18. -c with a passphrase source and no -e writes a plaintext archive (medium)

Where: runCreate in src/​internal/​cli/​ops.​go, and validate in src/​internal/​cli/​options.​go. Tested.
Problem. On create, the program reads the passphrase source only with -e. Without -e, --passphrase-file and --passphrase-env are ignored with no message. Design §10.3 says "A passphrase source means 'this archive is encrypted'", and --encrypt-index without -e is already a usage error.
Attack. No attacker is necessary. A user puts eictar -cf /mnt/offsite/backup.ect --passphrase-file /root/key /home in cron and forgets -e. Each run writes the whole tree in the clear to off-site storage, with exit 0. The next read with the passphrase file says "the archive is not encrypted; if it should be, it has been replaced or stripped", which points to an attack and not to the missing option.
Evidence. A create with --passphrase-file and no -e: exit 0, no output, and a later list with the passphrase file gave exit 3 with the message above. The review reproduced this on a separate build.
Fix. On -c (and -n -c), a passphrase source without -e is a usage error (exit 2). Do not make it imply -e: an explicit error is the same as for the other options.

Finding 19. A 7 KB plain archive makes a listing use 4 GB of memory (medium)

Where: CodecSpec.Params (map[string]any) in src/​internal/​format/​index.​go, and decModeFor in src/​internal/​format/​cbor.​go. Tested.
Problem. The decoder accepts any CBOR value in a codec parameter, also arrays and maps nested 32 levels deep. The bound on elements applies to each array, not to the whole index. The bound of finding 6 limits the bytes of the index (200 times its compressed size, at most 1 GiB), not the Go memory that those bytes decode into. An empty CBOR map is 1 byte, and becomes about 67 bytes of Go memory. Validate does not look at the parameters.
Attack. A plain archive has one catalog entry that no member uses, with parameters that hold 15 arrays of 4,194,304 empty maps. The 63 MB of CBOR compresses to 7 KB. Each user who lists, extracts, verifies, appends to, compacts or asks --info of the file pays the memory. The 1 GiB bound allows about 67 GiB, so the kernel can stop the process, and other processes. An encrypted index cannot be forged without the passphrase.

Finding 20. --repair removes a complete generation when its trailer magic is damaged (low)

Where: RepairArchive in src/​internal/​archive/​mutate.​go. Tested.
Problem. v1.1.4 made --repair refuse to remove a generation that looks complete, unless --discard-damaged is given (§9.5). The test of "complete" is the 8 bytes of the trailer magic alone. When the damage is in those bytes, repair takes the file for an interrupted write, and removes the newest committed generation with no question. Its index and the other 88 bytes of its trailer are good.
Attack. Not an attack: one bad byte in the last sector loses a committed generation, in the path that v1.1.4 made safe.
Evidence. A create, an append, then one byte changed at the start of the last trailer: --repair printed "removed 389 bytes; restored generation 1" with exit 0, and the appended member was gone. The same damage 76 bytes later was refused with exit 3, as intended. The review reproduced this on a separate build.
Fix. Also take the generation as complete when the last 96 bytes, with the magic left out, read as a trailer whose index ends at the trailer and whose generation follows the one before. Better, offer to write the magic again.

Finding 21. Blobs that overlap (low)

Where: validateMemberRanges in src/​internal/​archive/​reader.​go, copyBlobs and deadSpace in src/​internal/​archive/​mutate.​go, and pass B of src/​internal/​archive/​encrypt.​go. Tested.
Problem. Each blob must be inside the body, but two blobs can overlap. No writer of eictar makes that: shared content uses data, and a hardlink has no blob.
Attack. A plain archive of 1 MB holds one blob and 200 members that all point to it. --info shows a dead space of -208,666,624 bytes, and --compact (or --encrypt-archive) writes 210 MB. The output grows by about the blob size for each 4.5 bytes of index.
Fix. In validateMemberRanges, sort the blobs and dictionaries by offset, and refuse an overlap as a corrupt index. Apply the same rule in the second reader, and state it in format.md §8. Treat a negative dead space as damage.

Finding 22. A member id of 2^64-1 wraps the next id to 0 (low)

Where: OpenAppend in src/​internal/​archive/​writer.​go (maxID + 1), and src/​internal/​archive/​dedup.​go. Tested.
Problem. With an old member of id 264-1, the first new id is 0. Dedup then counts each old owner as written by this run, so it shares old content without the check that design §4.3 describes ("an old owner is checked before it is first used").
Attack. A plain archive holds a member with id 264-1, and a member whose digest is that of a file the victim will append, with other bytes in its blob. The victim's append shares the bad blob, and ends with exit 0. --verify and extraction find it later with exit 3. With a normal id, the same append warns and stores the file in full.
Fix. In Validate, refuse an id above a bound such as 263. In OpenAppend, refuse an id that wraps. In dedup, keep the set of the old ids, and do not compare ids.

Finding 23. --repair takes quadratic time on crafted trailers (low)

Where: the scan of RepairArchive in src/​internal/​archive/​mutate.​go, which calls Reader.load for each match of the trailer magic. Tested.
Problem. Each candidate trailer with a correct CRC can claim the index from the body to its own position. The scan reads and hashes that index before it compares the digest, so the work is about n2/192 bytes of BLAKE3 for a file of n bytes.
Attack. --repair or --repair -n of a file from someone else. Memory stays small. The user can stop the run.
Evidence. 1.9 MB took 5 s, and 3.8 MB took 15 s (65 s of CPU). Each doubling of the size made it 3 to 4 times slower.
Fix. Give the scan a budget of bytes to hash, for example 4 times the file size plus 1 GiB, and stop with exit 3 when it is used. Do the cheap checks first: the index must end at the trailer.

Finding 24. Large chunks exceed --memory-limit (low)

Where: boundByMemory in src/​internal/​archive/​extract.​go, and the xz decoder in src/​internal/​codec/​xz.​go. Tested.
Problem. The bound counts two buffers of the chunk size for each worker. xz makes a third, a dictionary of the chunk size for each chunk. No GOMEMLIMIT is set, so the garbage of each chunk stays until the heap doubles. The chunk size comes from the index, up to 256 MiB.
Evidence. --verify --memory-limit 512M reached 806 MB with zstd and 1.35 GB with xz, on archives of 263 KB and 1.3 MB.
Fix. Give each codec a DecodeMemory(chunk), as EncodeMemory does for the writer, and count it. Keep the xz dictionary in the decoder. Call debug.SetMemoryLimit when --memory-limit is given.

Finding 25. --info writes codec names and parameters with no escape (low)

Where: writeInfo in src/​internal/​cli/​mutate.​go. Tested. Two parts of this review found it separately.
Problem. The fix of finding 12 escapes names on a terminal. The listing escapes the codec cell too. But --info writes each catalog entry as it is, also an entry that no member uses, and Validate does not check catalog names.
Attack. A catalog entry named zstd\x1b[2J\x1b]0;pwned\x07: eictar --info -f evil.ect on a terminal clears the screen and sets the window title.
Fix. Pass each string from the archive through namesFor(stdout) in writeInfo, with a test like TestNamesOnATerminal. Refuse a catalog name that is not a known codec, and a parameter that is not printable.

Finding 26. An append to a substituted plaintext archive stores new content in the clear (low)

Where: OpenAppend in src/​internal/​archive/​writer.​go, and the option rules in src/​internal/​cli/​options.​go. Tested.
Problem. Design §14.4 documents the downgrade for reads: without a passphrase option, a plaintext archive in place of an encrypted one opens with no prompt. A write then stores new content in the clear. A user at a terminal cannot ask for the check: only a passphrase file or variable turns it on, and -e on -r is a usage error.
Attack. An attacker who can write the archive file, but has no passphrase, puts any plaintext archive in its place. The user runs eictar -rf backup.ect new/ as usual. No prompt comes, the run ends with exit 0, and new/ is in the clear.
Fix. Accept -e on each operation on an existing archive, as "this archive must be encrypted": prompt as now, and refuse a plaintext archive. A configuration key such as require-encryption lets a user set it once. Document the case in §14.4 and in the man page.

Finding 27. With --encrypt-index, the trailers show counts and sizes for each generation (low)

Where: the trailer (src/​internal/​format/​trailer.​go) and the append path of src/​internal/​archive/​writer.​go. Tested.
Problem. Design §14.1 says that with --encrypt-index "an observer sees only that the archive exists, and its total size". But each trailer shows, in the clear, the generation, the offset and length of the index, and the live member count. An append writes after the old trailer, so each earlier trailer stays until a compact.
Attack. An observer with no passphrase reads, for each generation, the number of live members, how many were added or removed, and the bytes that it added. When a generation adds one file, its stored size is exact.
Fix. Correct design §14.1, the man page and the README. A sealed member count is possible in a later format version, but the old trailers of an append stay in the clear until a compact.

Finding 28. With --encrypt-index, the length of the index lets an attacker test a name (low)

Where: the seal of the index in src/​internal/​format/​index.​go: compression, then the seal, with no padding. Tested.
Problem. The trailer gives the exact length of the sealed index (finding 27). The index is compressed before it is sealed, so a name that repeats part of another name makes the index shorter. This is the setting of finding 7, for names in place of content. Design §14.1 documents it for content only.
Attack. A user who can add files to the tree, and see the archive after each backup, adds a file whose name is a guess of a secret name. In a test, the right guess made the sealed index 7 to 8 bytes shorter at the median of six runs.
Fix. Document it in §14.1. In code, pad the sealed index to a bucket size, or do not compress a sealed index.

Finding 29. Create keeps the group bits, but not the group (low)

Where: createTemp in src/​internal/​archive/​writer.​go. Tested.
Problem. The new archive gets the mode bits of the old one, but its group is the primary group of the user who creates it. Compact keeps the group.
Attack. An archive is -rw-r----- user:backup. The user creates it again, and the new file is -rw-r----- user:users. Every member of users can then read it. No attacker acts. The user does not see the change.
Fix. Do as compact does: keep the old group when the system permits it, and clear the group bits and warn when it does not.

Finding 30. The temporary file of create is wider than the old archive for a short time (low)

Where: createTemp in src/​internal/​archive/​writer.​go. Tested.
Problem. The temporary file is made with mode 0666 less the umask, and gets the mode of the old archive after that. When the old archive is 0600 and the umask is 022, the file is 0644 for a short time. A descriptor opened in that time can read the whole new archive later.
Evidence. A watcher with inotify opened the file before its chmod in 10 of 2000 creates.
Fix. Make the temporary file with mode 0600, and set the final mode at the end, as compact does.

Finding 31. A failed write of the output gives exit 0 (low)

Where: the output of -t, -tv, --info, the summary of --verify and the list of -n, in src/​internal/​cli/​ops.​go, src/​internal/​cli/​mutate.​go and src/​internal/​cli/​dryrun.​go. Tested.
Problem. These paths ignore the error of each write. --json checks it and gives exit 4.
Attack. A script runs eictar -tf a.ect > manifest on a full disk. It gets a short manifest and exit 0, and keeps it as correct.
Fix. Write the output through a bufio.Writer, and give exit 4 when its Flush fails.

Finding 32. The check of a passphrase file does not look at its write bits or owner (low)

Where: passphraseFileExposure in src/​internal/​cli/​access_​unix.​go. Tested (the mode); Code (the owner).
Problem. The fix of finding 8 warns when others can read the file. On Unix it does not warn when others can write it, or when another user owns it. On Windows, another owner gives a warning.
Attack. Root encrypts backups with a passphrase file of mode 0622, or one that another user owns. That user writes a passphrase of their own into it before the run, and can then read the backups.
Fix. Also warn when the file is writable by group or others, or owned by a user other than the caller or root. Check the open file, so that the check and the read are of the same file.

Finding 33. Windows: x.. names the destination (low)

Where: IsStoredPath in src/​internal/​fsutil/​path.​go, and os.Root on Windows. Code only.
Problem. IsStoredPath splits a path only on /. On Windows, os.Root cleans x\.. to ., and removes trailing dots and spaces. So a directory member x\.. names the destination, and f, f., F and a\..\f are one file. os.Root still refuses :, reserved names and a path that escapes, so nothing leaves the destination.
Attack. An archive changes the times and the read-only attribute of the destination, and goes round the rules on collisions. Windows restores no owner, mode or xattrs, so the effect is small.
Fix. On Windows, refuse a member path with \, :, a part that ends in a dot or a space, or a reserved name. Compare paths without case for collisions. The fix of finding 13 closes the case of the destination on all systems.

Finding 34. chown after the xattrs removes file capabilities (information)

Where: writeFile in src/​internal/​archive/​extract.​go: the xattrs, then fchown, then fchmod. Code only.
Problem. On Linux, fchown of a regular file clears security.capability. So -p --preserve-owner as root never restores a file capability, which design §7.7 says it does. --diff-extract as root reports a false difference for each such file. The failure is safe: a capability is lost, never added.
Fix. The owner first, then the xattrs, then the mode. Test it in the CI job that runs as root.

Finding 35. The creation time in the header is not authenticated (information)

Where: src/​internal/​format/​header.​go; the keyed index digest covers the uuid, the generation and the index, not the header. Tested.
Problem. With no passphrase, an attacker can set the creation time of an encrypted archive. --info shows the new time, and --verify passes. Design §14.4 names only the trailer flags as a field without authentication. The uuid is bound into each key, and a change of the other fields breaks the read.
Fix. Name the creation time in §14.4. In a later format version, bind the header into the input of the index digest.

Finding 36. A rollback needs no old copy (information)

Where: the append path of src/​internal/​archive/​writer.​go. Tested.
Problem. Design §14.4 documents a rollback as putting back an older archive. But an append writes after the old trailer, so the current file holds each earlier generation until a compact. To cut the file after an earlier trailer is enough: the archive opens, --verify passes, and deleted or replaced members come back. A --repair after damage at the end does the same.
Fix. Say in §14.4 and the man page that a truncation is a rollback, and that only --compact removes the earlier generations. The defence stays the same: record the uuid and the generation in another place.

Finding 37. After an append, the data key is not set to zero (information)

Where: OpenAppend, Writer.Close and Writer.abort in src/​internal/​archive/​writer.​go. Code only.
Problem. The writer borrows the keys of the reader, and no code sets them to zero after -r, -u or --delete. Design §14.2 says that the reader sets the data key to zero when it closes. Create, compact and the change of passphrase do.
Fix. Call Keys.Zero in Writer.Close and Writer.abort for a writer that OpenAppend made.

Finding 38. --json writes C1 and text-direction characters as they are (information)

Where: the JSON output in src/​internal/​cli/​ops.​go. Tested.
Problem. encoding/json escapes C0 characters, but not U+0080 to U+009F or the text-direction characters U+202A to U+202E and U+2066 to U+2069. Design §10.13 says that --json escapes each name. On a terminal, a crafted name can show as another name.
Fix. Write these characters as \uXXXX after the encode, which is valid JSON, or correct the design.

Finding 39. With -h, a link changed to a FIFO after the walk makes the open wait (information)

Where: osSrcPaths.Open in src/​internal/​archive/​src.​go, which opens with no O_NONBLOCK. Tested through a test hook.
Problem. A user who can write the tree points a link at a file, then at a FIFO after the walk. A -h backup waits for ever, with no message. -h follows links by design (§14.5), so the effect is a hang only.
Fix. Open with O_RDONLY and O_NONBLOCK, as the other opens of the walk do.

Finding 40. No signal handling (information)

Where: the program has no signal.Notify. src/​internal/​cli/​password_​unix.​go restores the terminal in a defer. Tested (the temporary file); Code (the prompt). Two parts of this review found the prompt case separately.
Problem. SIGINT or SIGTERM during a create leaves the temporary file .NAME.create-*, with the mode of the old archive and a part of the archive, in the clear unless -e. A later walk of that directory stores it. A compact leaves .NAME.rewrite-*. Ctrl-C at the passphrase prompt ends the process before the defer, so echo stays off.
Fix. Catch SIGINT, SIGTERM and SIGHUP: restore the terminal, remove the temporary file, and exit with 130 or 143.

Finding 41. Windows: -f follows junctions, and a rewrite drops the ACL (information)

Where: MayFollow in src/​internal/​meta/​meta_​windows.​go, and the rewrite in src/​internal/​archive/​mutate.​go. Code only.
Problem. On Windows, checkLinks does nothing, so a junction that another user made on the path is followed, and the rename replaces its target. Compact, the change of passphrase and --encrypt-archive write a new file that inherits the ACL of the directory, so an explicit ACL on the archive is lost. Design §15.1 says that modes are not kept, but does not name the ACL.
Fix. Copy the DACL of the old file before the rename. Refuse a reparse point in -f that the caller does not own, or document the case.

Finding 42. Shared content allows a ratio of 70,000 to 1 at extraction (information)

Where: shared content, §4.3. Tested.
Problem. This is the feature as designed: each member that shares content is written in full. A plain archive of 1.4 MB lists 105 GB. With an owner of 1 GiB of zeros, the same index gives about 100 TB. Design §14.3 does not name this cost beside the decompression bombs.
Fix. Document it in §14.3. The user sees the total in -tv and --info before an extraction. An option such as --max-extract-bytes, or a check of free space against the selected total, lets a script bound it.

Finding 43. An unknown codec name gives exit 4 (information)

Where: ErrUnknownCodec in src/​internal/​codec/​codec.​go, and exitCodeFor in src/​internal/​cli/​run.​go. Code only.
Problem. An archive that names a codec that this build does not have is "too new or damaged", which is exit 3 (§10.7). The error has no mapping, so it gives exit 4, an I/O error.
Fix. Map codec.ErrUnknownCodec to exit 3, with a test.

Finding 44. A member id can be used again after a compact (information)

Where: OpenAppend in src/​internal/​archive/​writer.​go. Code only.
Problem. --compact drops a tombstone with the highest id, and the next append takes the highest id plus one. So an id comes back. format.md §8.3 says that an id is never used again. Each new blob has a new salt and key, so this has no effect on the cryptography.
Fix. Keep the highest id ever used, for example in the index, or correct format.md §8.3.

5   What the review found sound

  • Nonces and keys. A test read every index of 22 generations from two full life cycles: create with a trained dictionary, -u, -r, --delete, compact, recompress, change of passphrase and --encrypt-archive. It found 1475 salts, and none sealed two different ciphertexts. The HKDF info strings cannot collide, no key has two purposes, and the wrap binds the archive uuid.
  • What the AADs bind. A chunk binds the member id, its index and the last-chunk flag, which the reader takes from the authenticated index, so truncation and reorder fail. The index binds the generation, and its key binds the uuid. A dictionary binds its id. The review found no gap.
  • Index authentication. In an encrypted archive, the keyed index digest is checked first, in constant time, before any decompression or decode. A member without a seal in an encrypted archive is refused, and the reverse fails.
  • KDF limits. A crafted crypto header with time 65, or memory 232-1, is refused with exit 3 before the prompt.
  • Parsing. The header, trailer and crypto header are checked before any allocation that their numbers decide. Validate covers ids, types, sparse maps, the chunk table, shared content, hardlinks and dictionaries with no overflow. No input made the program panic.
  • Decoders. The zstd window, the s2 length, the bound of gzip, flate and xz, the bytes after a stream, and the dictionary size all hold. 33,281 changed dictionaries given to the zstd encoder made no panic and no failed round trip.
  • Extraction. .., absolute paths and links that lead out are refused. Pipes and devices use *at calls with one name. Temporary files are random, O_EXCL and 0600, and removed on error. A hardlink links only to a file of this run. The umask, setuid and xattr rules hold. --strip-components cannot give an empty path. The dry run makes nothing.
  • The scratch directory of --diff-extract. It is made by os.MkdirTemp with mode 0700, all work in it is by unique names through os.Root, and it is removed at the end. Another user in /tmp cannot enter it.
  • The walk. Each directory is held, each file is opened by one name, and its device and inode are checked. FIFOs and devices are never opened. Spill files hold sealed chunks only, are 0600, and are removed at once.
  • Locks and the write sequence. The lock is taken before the trailer is read, and the path must still name the locked file. An append writes its index before its trailer, and an abort cuts the file back.
  • Configuration. No file is read from the current directory. The owner and mode of the configuration file are checked on the open file. Passphrase keys are refused in it. --no-config ignores the file and the environment.
  • Messages. Each error and warning, and the lines of -t, -tv, -v, -n and --diff, escape names on a terminal (except findings 25 and 38).

6   Order of work

The review suggests this order, from the effect on a user and the size of the fix:
  1. Findings 13 and 14 together: one resolution of member paths with no link following, also for the metadata of the last phase. Correct design §14.3.
  2. Findings 15, 16 and 17 together: one resolution of -f in a single pass, with the operations relative to the parent directory, and the rule of fs.protected_regular for an existing file.
  3. Finding 18: a usage error. A small change.
  4. Finding 19: parameters as integers and strings only, and a bound on the decoded memory.
  5. Finding 20, then the other low findings. Findings 25, 31, 32, 37, 39 and 43 are each a small change.
  6. The documentation findings: 26, 27, 28, 35, 36, 42 and 44.
Each fix needs a test that fails without it, as for the first review.
