eictar — Testing

Date: 2026-10-15 Applies to: v1 (format version 1.0)

This document describes how eictar is tested, and the evidence that the tests give. design.md describes the format and the program, and history.md gives the milestones and the releases. This document was §13 of design.md until 2026-10-15. Its section N was section 13.N there.

Contents

1. Unit tests · 2. Operational tests · 3. Supporting tools · 4. Stress tester · 5. Assurance plan

Tests are part of each deliverable. There are two levels: unit tests next to the code, and operational tests that run the built binary as a user does. A milestone in history.md is not complete until both levels cover it.

Every item in the lists below exists now, except the items marked “later”.

1. Unit tests (in each package, go test ./...)

  • Format round trip: members of all types, every codec, plaintext and encrypted, index sealed and not sealed.
  • Structure encoding: encode and decode of the header, the trailer and the crypto header, every CRC, every limit, and the refusal of each single-field corruption.
  • Codec conformance: one test suite for every registered codec. It covers round trips, empty input, incompressible input, chunk boundaries, the parameter checks, refusal of bad parameters, and the parallel-encoder test of design.md §8.2.
  • Key schedule: fixed vectors for the KEK, the wrapped data key, and every subkey. Also for a sealed chunk, a sealed index, a sealed dictionary and the keyed index digest. A failure here means that existing archives no longer open. It never means “update the vector”. The vector of the dictionary key was also calculated apart from the code, from the definition in doc/format.md.
  • Chunked AEAD: tag checks, a wrong key, a chunk moved to another index or member, a changed final flag, and truncation. Each must fail.
  • Crafted archives: the reader must refuse each of these:
    • a member path with ../, or an absolute path
    • a link to a place outside the destination, followed by a write through it
    • a large chunk size
    • a blob outside the body
    • a regular file without a digest
    • a member that shares content with a member of other content, or with no blob
    • a dictionary that the index does not hold, or on a codec other than zstd
    • KDF parameters above the limits
    • a downgrade to plaintext
    • changed metadata in an encrypted archive
    The crafted-KDF test fails if the check is removed. This proves that the test catches the fault.
  • Path rules: StorePath, IsStoredPath and Match, with hostile inputs: ../ escapes, absolute paths, and paths that are not canonical.
  • Fuzzing (go test -fuzz): the header, the trailer, the crypto header, the index decoder, the decoders of the codecs, the openers of a sealed chunk, index and dictionary, whole archives changed from the golden ones, the pattern rules, the compression spec and the configuration file. A malformed archive must give an error. It must never cause a panic or an unbounded allocation. §5, step 4, gives the rule of each target.
  • Race: all tests under -race, with -j from 1 to 64.
  • Configuration: the precedence of the four levels, codec defaults, and the search order of the files. Unknown keys and variables are usage errors that name their line or variable, and so are a passphrase and the other refused keys. Also: the scope of a configured value, a group-writable file, --no-config, comments, --show-config with its sources, and the variable of --passphrase-env. A .eictarrc in the current directory has no effect.
  • Encoder memory (design.md §8.2):
    • the window of zstd fits the chunk
    • the estimate of each codec
    • a limit on the compressions at once
    • the number of states for each amount of RAM and each memory limit
  • Codecs, worst case: each codec at its strongest setting compresses 4 MiB of zeroes in less than 10 s. The test proves why the xz binary tree is not used (design.md §10.2).
  • Lock: while one writer holds an archive, append, delete, compact, repair and create each stop with ErrLocked. A lock on a file that a rename replaced is refused (design.md §9.6).
  • Recompress: the content, the digests and the ids stay, and each sealed member gets a new salt. A tombstone behind a hardlink, and the holes of a sparse file, survive (design.md §9.3).
  • Progress meter: the status line, no drawing before the first byte, and no meter without a terminal (design.md §10.10).
  • Compare with the disk: each kind of difference, patterns and excludes, a file archived alone, an encrypted archive, the same result for each -j, and a link on disk that leads out of the directory (design.md §9.8).
  • Compare with an extraction: --diff-extract finds a change that a digest with a fault hides from --verify and --diff. It finds a wrong byte, mode, time or attribute in the extracted copy. It compares times to the precision of the scratch file system, and leaves out an attribute that the scratch refuses, with a notice. It reports each cause once. It refuses a scratch directory in the tree, and stops with a message on a full scratch. Damage gives exit 3, also under --keep-going. The result is the same for each -j. Each operation on the scratch directory, and each on the tree, fails in turn, and each fault fails the run. As root, a wrong owner and other device numbers of a copy are differences (design.md §9.10).
  • Dry run: for create, update with each mode, extract with each overwrite policy, and delete, the paths of the dry run are the paths that the real run writes, and the archive does not change. Also the conflict policies, the key for the digests of an encrypted archive, an unsafe member path, and no destination made (design.md §9.9).
  • Strip components: the paths after the strip, a short path left out, the later member of a collision with its warning, two directories with one path, a hard link to a target that is extracted and to one that is not, patterns on the archive paths, the dry run, --diff with patterns, excludes and a hard link, a path that is not canonical, and exit 1 (design.md §10.14).
  • Security regressions: one test for each finding of doc/Security_Audit.md:
    • the decision for each class of xattr
    • a member .
    • a file that becomes a link after the walk
    • a directory that becomes a link during the walk, before and after the walk opens it
    • the rule for links in the archive path
    • the umask
    • the expansion of the index
    • a passphrase file that other users can read
  • Names on the terminal: each kind of escape of design.md §10.13. A name with an escape sequence in -t, -tv, a dry run and --diff: escaped on a terminal, and exact to a pipe. A message is escaped in both cases.
  • Man page and help: doc/eictar.1 and --help name every long option of the parser, and the help gives each short form. No line of the help is wider than 80 columns.
  • Bash completion: completions/eictar.bash lists each option of the parser with its short form, each codec, and the values of --update-mode and --on-conflict, and nothing more. A second test runs the script in bash. After each option that takes a value, the script must offer values and not options. After any other option, it must offer options. The test also covers -f, -cf, --file=NAME, a name with a space, and environment variable names. Windows skips it.
  • Platforms: each metadata test runs where meta.Supports says that its feature exists. An xattr from macOS and one from Linux, extracted on each platform, are applied or listed in the one notice as design.md §7.7 says. A pipe is created, or skipped with a notice on macOS.
  • Golden files: four archives in src/internal/archive/testdata/golden/. plain.ect and encrypted.ect each have three generations: a create, an append that replaces a member, and a delete. dict.ect is encrypted, with a sealed dictionary. shared.ect has a reference to a live owner and a reference to a tombstone. The tests open them, run --verify on them and extract them. Only a planned format change can write them again, with -update-golden.
  • Dictionaries (design.md §4.2):
    • a gain on similar files
    • a frame that decodes only with its own dictionary
    • a dictionary within its size, and training that fails cleanly
    • reuse on -r, compact and recompress
    • damage to a plain and to a sealed dictionary
  • Identical content (design.md §4.3):
    • copies that share one blob, and --no-dedup
    • sharing across generations, and with an earlier version
    • a damaged old owner, which is not used
    • delete, compact and recompress
  • Selection: -R and --exclude-regex on the walk and on each read, a whole-path match, and an -R that matches nothing. An --exclude glob with a / takes the contents of a directory on a read, for -t and --diff (design.md §10.11). The .ect name rule (design.md §10.12).
  • Mutation: append after the old trailer, each --on-conflict policy, and each --update-mode case of design.md §10.5. Also delete, --verify, --info, and the passphrase for each. Compact runs plain and encrypted, through a symbolic link, and with a hardlink to a tombstone. Two tests check --keep-going. A path that fails keeps its old member. A hardlink never points to a member that failed.
  • Crash consistency: an append, cut at each byte between the old and the new length. Each cut must fail to open, and --repair must give back the old file exactly. A torn trailer gives the same result. The writer only appends, and it syncs before the trailer. Thus a crash leaves a prefix of the writes, and the cuts cover each crash point.

2. Operational tests (end to end, build tag operational)

These tests run the compiled eictar binary in a temporary directory. They check its exit status, its output and the resulting files. They never call internal packages. They prove that the program works, not only that its parts work.

  • Lifecycle: create, list and extract, with a comparison against the original tree. Then append (with other codec settings), delete, --info, --verify, compact and --verify again, plain and encrypted.
  • Concurrency: the same input at several -j values gives the same content and the same listing.
  • Encryption: round trips with a sealed and with a plain index. A wrong passphrase gives exit 3. With no passphrase and no terminal, the message names the options to use. The environment-variable source works, with its warning. A plaintext archive with a passphrase source gives exit 3.
  • Paths and links: stripped absolute paths, -d, the archive that contains itself, symbolic links, and -h.
  • Damage: a changed byte gives exit 3, and a missing archive names the file.
  • Update modes: a touched file that digest skips and newer takes. The unit tests of §1 cover each mode and case.
  • Mixed archives: members from separate appends, with different codecs and parameters, all extracted in one pass.
  • Refused mutations: --on-conflict=error and a --delete pattern with no match give exit 2, and the archive is unchanged.
  • Listing: -t gives the paths, and -tv and --long give the same long listing. -tvv adds its columns and the line of totals. --json has every field of design.md §10.9.
  • Metadata: hardlinks, holes, xattrs, setuid bits, pipes, link times, a skipped socket, and difficult names (spaces, newlines, non-UTF-8, long names, leading dashes). The test compares the result with os.Stat, xattr reads and the allocated blocks, so that holes stay holes. It runs with a plain and with an encrypted archive. The ownership and device tests need root, and skip with a reason when the user is not root.
  • Crash consistency: a real append is killed with SIGKILL part way through. The list must fail with exit 3 and name --repair. Then --repair must give back the old file exactly.
  • --verify: a changed byte in a blob gives exit 3, and the message names the member. --quick passes, because it reads no member data.
  • Configuration: a configuration file in HOME sets the codec, -v names the file, a misspelled variable gives exit 2, and --show-config runs with no operation. The unit tests cover the refusals. A file that another user owns needs a second user, so no test covers it yet.
  • Lock: two real appends at the same time. The second stops with exit 4, and the first completes.
  • Every codec: members from six codecs in one archive, from separate appends. One pass lists them, one runs --verify, and one extracts them.
  • Recompress: a bad spec gives exit 2 and changes nothing. A good one changes the codec of every member, and the extracted tree is the same.
  • Progress: with stderr not a terminal, --progress writes nothing there.
  • Change of passphrase: the new passphrase opens the archive, the old one gives exit 3, and the new KDF parameters are in effect.
  • Newer features:
    • -R on create and on extract
    • the .ect name
    • a dictionary, in --info and in the listing
    • shared content, in the listing, in --info and in --json
    • --diff: no difference after -xp, except the pipe on macOS, and then a changed file and a missing file with exit 1 (design.md §9.8)
    • --diff-extract: no difference in the source tree, no scratch directory after the run, and a changed file with exit 1 (design.md §9.10)
    The dry run (design.md §9.9) has no operational test. The tests of package cli run it through Run, and check its output and that nothing changes.
  • Large archive: an archive larger than 4 GiB, plain and encrypted. make large runs it. Other runs skip it, because it needs time and disk space. The format stores offsets and lengths as CBOR uints, which take 8 bytes above 2^32. The test takes each of these past 2^32: the size of one member, the offset of a blob, the offsets of data segments in a sparse file, the index offset, and prev_index_offset. The data is random and the codec is none, so the archive is as large as its data. The test checks the sizes in --json, --verify, a full extraction, -O, --diff, an append, a cut append and --repair, and a delete with --compact. It compares each file with SHA-256. A reader that keeps only 32 bits of a blob offset fails --verify in this test.
  • Scale (nightly, later): 100,000 small files, and one file larger than memory.

3. Supporting tools

  • src/internal/testutil/ holds the fixture-tree builder, the tree comparison, and a helper that builds the binary once for each test run.
  • Code builds the fixtures. They are not committed as a tree, because git cannot keep modes, timestamps, hardlinks and holes exactly.
  • Tests that need root (ownership, device nodes) skip with a clear reason. A CI container with the necessary privilege must run them.
  • A skip passes quietly. go test does not show it without -v, and a platform avoids a test by skipping it. Thus make skips runs the tests with -json, and tools/testskips lists each skipped test with its reason, each failed test with its output, and the totals. A package that fails outside a test, as after a time-out, is listed with its output. Each CI job runs it after make check, so that a green job also says what it did not test, and a red job says which test failed, when it fails again in this second run. The job’s result stays the result of make check.
  • Coverage and mutation testing measure the tests (§5). format, crypt and codec need the strongest tests, because a fault there is silent and permanent. The benchmarks are make bench, make compare, and BenchmarkCodecs and BenchmarkDictSmallChunks in codec (design.md §8.4).
  • References to sections stay correct. The code and the documents refer to sections by number, such as doc/design.md 9.6 in a comment and testing.md §5 in a document. A section that moves leaves such a reference wrong. The test of tools/docrefs finds each reference, in the documents, the code, the Makefile and the workflows, that names a section or a document that is not there. A reference with no name of a document is to the document that holds it. In Security_Audit.md, it is to design.md.

4. Stress tester

make stress builds and runs tools/stress, and make stress-build builds it alone, as .build/stress, with .build/eictar-faults: eictar built with -tags faultinject, for the disk faults. It tests the built binary with random data and random operations, and it compares each result with a model. The unit and operational tests check the cases that someone thought of. The stress tester finds the combinations that nobody did.

The model is a map from each stored path to what an extraction must give back. That is the type, the content, the size, the mode, the time, and the target of a link. It changes only as eictar’s rules say (design.md §9.2, §10.5). Replace, skip, error, the three update modes, and delete with eictar’s pattern rule are each a few lines of the tester.

A sequence creates an archive from a generated tree, and then takes steps. Before most steps, the tree changes. A file gets new content, a new time or a new mode, or it goes, or it becomes a link, or new entries come. Then one operation runs: append with each --on-conflict, update with each --update-mode, delete, compact, compact with --recompress, extraction by pattern or by -R, --diff, a dry run, or --strip-components. Each operation uses a random codec and random settings: chunk size, workers, memory limit and spill threshold. A zstd dictionary at level 10 or above gets chunks of 64 KiB or more. Each chunk with such a dictionary costs approximately 0.5 ms (design.md §15.2), and chunks of 512 bytes on a large tree take more than the limit of two minutes for one command, which counts as a hang.

The last three steps test the operations that compare and plan:

  • --diff of a tree just extracted must find no difference. Then the tester makes one change to that tree: other bytes of the same size, a mode, a time, a file removed, a file added, or another link target. It keeps the time of the parent directory. --diff must then report that path with that kind of difference, and nothing else, with exit 1. Half the time, the step runs --diff-extract in place of --diff, with the scratch directory beside the tree. Then each copy must also equal its file, the one change must still give one line, and no scratch directory must stay.
  • A dry run of -r, -u, --delete or -x must list the paths that the model says the real run writes or deletes. The archive must not change, and -x -n must not make its destination.
  • --strip-components 1 or 2: half the time, the tester first appends a twin of an entry under a new top directory, so that two members get one path. The model gives the expected tree and the collisions. The dry run must list the paths after the strip, the extraction must give the expected tree, and --diff with the option must find no difference. Each must warn for each collision and exit with 1 when there is one.

Each sequence has a profile, the kind of tree that it works on. The seed chooses it, and -profile forces one:

Profile Tree What it takes eictar through
mixed 10 to 70 entries of every kind and size the general case
small 150 to 500 small source files that share a header and a shape dictionaries that train, many members
large 3 to 6 files of 1 to 24 MiB, and copies of them many chunks, chunks of 16 and 32 MiB, windows, shared content
versions medium files with exact copies, and near-copies with a few bytes changed shared content that must tell equal from almost equal

The settings vary with the features. A zstd codec can have train: with a small size, alone, or at 1 MiB. It can have long: alone, or with a window that a large chunk holds. -r and -u can have -R, --exclude-regex and --no-dedup, and create can have --no-dedup. The model applies -R and --exclude-regex as eictar does. An -R that matches nothing must be refused like a conflict.

At the end of each sequence, --info shows whether the archive holds a dictionary and shared content. The summary counts both, so that the coverage of these features is measured, not assumed.

A third of the sequences are encrypted, some with a sealed index. In these, a step can also change the passphrase. After the change, the old passphrase must fail with exit 3.

After each step the tester makes five checks:

  1. -t lists exactly the model’s paths.
  2. --verify passes.
  3. A full extraction gives back the model. The only extra paths allowed are the parent directories that extraction makes itself.
  4. The hardlinks of the extraction agree with the model. The model gives each file a link group. One run puts the names of one inode that it stores into one group. The names of a group must be one file, and the names of two groups must be two files. Each extraction of the tester . The second reader (§5, step 2) agrees. Its fields are those of -t --json, and its own extraction gives back the model.

Some operations must be refused: a conflict under --on-conflict=error, an -R that matches nothing, and a delete pattern that matches nothing. Each must exit with 2, and must leave the archive byte for byte as it was.

The data is random, text-like, repetitive or zeros, and it is often one byte on either side of a chunk boundary. The tree has deep directories, empty files, symbolic links, hardlinks, copies and sparse files. Its names have spaces, other scripts, and bytes that are not UTF-8 where the filesystem takes them. A name never holds a glob character, so that a path is a literal pattern.

The fault mode is on by default. It adds three tests:

  • A crash. After a change, the tester cuts the archive at a random point inside the new generation. The archive must be refused with exit 3 and a message that names --repair. Then --repair must give back the archive of before the change, byte for byte.
  • Damage. In a copy of the archive, the tester flips one to four bits, often in the index and the trailer. --verify and extraction must agree. Both must refuse the copy with exit 3. Otherwise both must accept it and give back the model exactly, because a bit in dead space harms nothing. Wrong content with exit 0 is the failure that this test looks for. The second reader must refuse the copy when eictar refuses it, and read each member when eictar accepts it.
  • A disk fault. The tester runs a change to the archive with .build/eictar-faults, and EICTAR_FAULT makes one operation on the archive file fail: the Nth open, create, write, short write, fsync, truncate, close, rename, remove or fsync of the directory. The change is an append, a delete, a compact, a recompress or a change of passphrase. A command that succeeds must leave the new state. A command that fails must exit with 4, and leave the old state or the new one, with no file beside the archive, except a temporary file whose removal was the fault. A change that commits with a rename must leave the old archive byte for byte, or the new one. A change in place may need --repair, which must then give back one of the two. One fault does not stop the rollback of a change in place, so that needs two faults or a crash after one, which the crash model of §5 covers. The tester prints a note and leaves the disk faults out when the binary is not there.

Any other exit code, a panic, or a command that runs for more than two minutes is a failure.

The summary starts with the result: PASS, or FAIL with the sequence. Then it gives each check, and the number of times that it held. A check that the run did not reach has the note [not reached in this run]. Then it gives the number of each operation, and the coverage of the profiles, dictionaries and shared content. Last, it gives the five slowest commands of the run. Each line has the time, the options, the size of the source tree, and the make stress command that repeats its sequence. A slow command is not a failure. Only a command that takes more than two minutes fails, as a hang. The list shows a slow case before it becomes a hang, as the case of design.md §15.2 became. After a failure, the counts are the checks that held before it. To a file or a pipe, the progress line comes once a minute.

A failure stops the run. The sequence’s directory stays, with the source tree, failure.txt and replay.sh. failure.txt gives the seed and each step. replay.sh repeats the eictar commands. All randomness comes from the seed, and the file times come from a clock of the tester, never from the system clock. Thus make stress STRESS="-seed N -sequences 1 -profile P" repeats a failed sequence exactly.

The tester is tested. A bug put into eictar on purpose, where -u took an equal time as newer, failed the sixth sequence. The report named the file and its wrong mode.

Findings. The first runs found three faults in eictar. Each one now has a test of its own:

  • A chunk that its codec refused, for example after a failed zstd checksum, gave exit 4, as for an I/O error. It must give exit 3, for damage. Such an error is now ErrCorruptData.
  • A pattern that matched a directory by its name, deeper in the tree, did not take the directory’s contents (design.md §10.11).
  • -u --update-mode=digest archived an unchanged sparse file again, when the filesystem reported its data regions in another way (design.md §10.5).

The steps for --diff, -n and --strip-components found two more in their first runs:

  • --diff reported the directory of a member as a path that the archive lacks, when -r a/b/c had added the member by its own path, with no member for a/b (design.md §9.8).
  • --diff --strip-components compared a hard link with the file at its target’s path when a collision had left the target out. Extraction gives such a link a copy of the content (design.md §10.14).

Longer runs found one more fault, and two faults in the tester:

  • A damaged crypto header that gave less than 8 KiB of KDF memory for each thread gave exit 4. It must give exit 3, for damage (design.md §6.2).
  • zstd:level=13,train=16K with chunks of 512 bytes took 124 s on a tree of 125 MiB, and the tester reported a hang. The output was correct. At level 9, the same command took 0.6 s. This is the cost that design.md §15.2 records.
  • After 4 hours, the generator gave two new entries of one directory the same name, and the second one failed. A new entry now gets another name when its name is taken. After this fix, a run of 8 hours passed. make check now runs the tests of tools/ too.

A run of ten minutes, over all the profiles, made 146 sequences. They ran approximately 14,000 eictar commands, with 256 crashes and 510 damaged copies. 51 sequences ended with a dictionary, and 124 with shared content. With the new steps, a run of five minutes made 106 sequences and 10988 commands. It ran 207 --diff steps, 305 dry runs and 161 extractions with --strip-components.

5. Assurance plan

The goal is evidence that eictar can hold data in a mission-critical use. Tests cannot prove that a program is correct. Thus this plan collects evidence of different kinds, and each kind finds faults that the others do not find:

  • the strength of the tests, measured
  • a second implementation, from the specification only
  • faults of the disk and of the machine, injected on purpose
  • hostile input, generated
  • models of the protocols, checked by a tool

The critical promise is that a user gets back the data that went in, or gets an error. Wrong data with exit 0 is the worst failure. Each step below tests that promise from a different side.

Step 1. Measure the strength of the tests.

  • Coverage of all the tests together. Unit coverage alone does not count the operational tests, because they run the binary. make cover builds the binary with coverage, runs the unit tests and the operational tests, and merges the two results.
  • Tests as root. Linux and macOS run the tests as an ordinary user, and the BSD virtual machines run them as root. A CI job runs the tests on Linux as root too. Then each platform family runs the code for the owner, the device nodes and the privileged xattrs at least once.
  • Mutation testing. tools/mutate makes one small change to the code at a time: a comparison, an operator, or a condition. Then it runs the tests. A change that no test finds is a survivor. A survivor in code that the tests run is a check that no test checks. make mutate runs it.

The result of step 1 is a list of gaps, in order. That list decides where steps 2 to 4 start.

How tools/mutate works. It parses each file of the package that builds on this platform. It makes these changes, one at a time:

  • a comparison to its boundary and to its opposite (< to <= and >=)
  • == to !=, && to ||, and the reverse of each
  • an arithmetic, bitwise or shift operator to its pair (+ to -, << to >>)
  • a ! removed, and ++ to --
  • the condition of each if to false, so that its check never runs

A run of the tests first gives the coverage. A mutant in code that no test runs is not covered, and its tests do not run. A coverage profile has no block for the expressions of a case, for a declaration outside a function, or for the rest of a statement after a function literal in it. Thus a case expression takes the coverage of its switch, a declaration outside a function always counts as run, and the rest of a statement takes the coverage of its start. The last rule came late: in if err := applyOwner(m, func(…) {…}); err != nil {, the condition showed as not covered, and the accepted list hid it. Each other mutant goes to the compiler through an overlay in GOFLAGS, so the source tree never changes, and mutants run in parallel. A go build that a test runs inherits GOFLAGS. Thus the binary that the operational tests build has the mutant too, and with -tags operational and -test for their package, they count. With -tags, a second run without a mutant gives the coverage of that binary: it writes it to GOCOVERDIR, as for make cover, and the tool adds it to the coverage of the tests. A second run is necessary, because with -cover, go test gives each test process a coverage directory of its own. Each go command runs in a process group of its own, and the tool kills the group when the command ends. A mutant can make the binary loop for ever, and when its test stopped at the time limit, the binary stayed: one run left 18 of them, each on a core. A failed test finds the mutant. A test binary that does not end in three times the time of the first run stops, and that also finds the mutant. With -j, the mutants share the machine, so a slow run can pass that limit with no hang. Thus each mutant that stops runs again alone, and only a second stop finds it. On archive, before this rule, 156 of 388 mutants stopped under -j 8. A mutant that does not compile does not count. The score is the part of the counted mutants that the tests find. -test gives other packages whose tests run, so that a run can tell a gap of one package from a gap of the whole program.

The accepted list. Some mutants cannot be found by any test, or by no test of a run of make mutate. tools/mutate/accepted.txt lists them, and make mutate does not count them. An entry names the file, the function and the change, in the form that the report prints. Thus an entry stays correct when lines move. Each entry must give one of four reasons:

  • Equivalent: the change cannot change what eictar does, for example the error of crypto/rand.Read, which never returns one.
  • Too costly: a test needs what a unit test cannot have: more memory than a test can use, a file system on which a given call fails, or a count of the open descriptors of the process. The entry says what the test needs, and names what else stops the input or covers the risk.
  • Needs root: only root can run the code, such as a device node or an owner, and make mutate does not run as root. The entry names the test that the CI job as root runs.
  • Another platform: the code runs only on a platform where make mutate does not run. The entry names the platforms.

An entry whose mutant the tests find, or that names no mutant, fails the run. Thus the list cannot keep an entry that is no longer true.

These tests compare the second reader with eictar:

The second reader found three gaps in the specification, one fault in the reader of eictar, and one fault in the writer:

  • format.md §8.3 said that a member that is not reg has no off. But eictar 1.1.0 and earlier wrote an off on each member with no blob, of each type, as the golden archives show. The rule for the old writers now says so.
  • format.md §8.1 said that the map keys are “sorted bytewise”, and not of what. The order is that of the encoded keys, so a shorter key comes first. No reader checks it.
  • After a compact of an archive whose members were all deleted, the index held members as null, and format.md §8.2 asks for an array. The stress tester found it. The writer now writes an empty array (TestIndexNoMembersIsAnArray). A reader accepts null, because eictar 1.1.1 and earlier wrote it.
  • format.md §6 gave no bound on the window of a zstd frame. eictar refused a window larger than the chunk size and 1 MiB, and the second reader took any window. Thus a frame that asks for 24 MiB, in a chunk of a few bytes, was damage to eictar and correct to the reader. FuzzArchive found it in the second run of the gate (step 6). format.md now gives eictar’s bound, and the reader refuses a larger window. A test makes sure that eictar’s writer never asks for more.
  • eictar took a map key for a field of another case: salT for salt in the crypto header, Path for path in the index. The CBOR library does this by default. format.md §8.3 says that a reader ignores a key that it does not know, so the second reader found no salt and refused the archive, but eictar read it. FuzzArchive found it after the gate, in a run of 5 minutes. eictar now matches a key only by its exact bytes (TestKeysMatchExactly), and format.md §8.1 says so.

Step 3. Faults of the disk and of the machine. A layer under the writer makes a write, an fsync or a rename fail, or makes a write short. A power-loss mode records the writes, and drops or reorders the writes that were not synced. After each fault, the archive must open as the old generation or as the new one, or --repair must give back one of them. The stress tester injects these faults at random.

Part 1, faults that the program sees, is done:

  • In archive, each operation on an archive file and on its directory goes through a fileSystem (fs.go). In production, it is the operating system. TestFaultsLeaveTheOldOrTheNewArchive makes each of these operations fail in turn. It does this for create, create over an archive, append, delete, compact, recompress, repair and a change of passphrase, and for a create, an append, a compact and a recompress with a dictionary, plain and encrypted. A write that fails writes half of its bytes and gives ENOSPC. Each other operation gives EIO. After each fault, these rules apply:

    • The archive holds its old state or its new state. Only a fault in the truncate that undoes an append can make a repair necessary.
    • A run that reports success made the new state.
    • A run that reports success had no fault. There are two exceptions: a chown, which a user that is not root cannot always do, and a close of a file that the run did not write.
    • The error is the fault itself: an I/O error, not damage.
    • No file stays open, and no temporary file stays behind.

    TestReadFaultsAreNeverSilent does the same for extract and verify. Three faults put into the writer on purpose were each found. The rule on success came after a mutation run (below). It found two errors that the program ignored, and both are now fixed:

    • Writer.SameFile did a stat of the archive for each file of the walk, and gave “not the same file” when the stat failed. If the archive was inside a path to archive, it could then go into itself. The writer now does one stat when the archive opens, and a failure stops the run.
    • Repair ignored the error of its last close. After the fsync, this error can still report a lost write, on NFS for example.

    The rule that the error is the fault found one more: a read that failed while repair loaded a generation counted as damage. Repair then said that the archive had no complete generation (exit 3), when the disk had failed (exit 4). Now only damage, or a version that this build does not read, rejects a generation. The second matters for an archive of archives stored without compression: it holds the trailers of its members, which a later version can have made.

    Under -race, each run of the dictionary case trains a dictionary, which is slow. Thus, under -race, that case tests one fault in seven. The runs without -race (make skips, make check-norace) test each fault.

  • In pipeline, each spill file comes from newSpillFile. TestPipelineFaults makes each operation on a spill file fail in turn, and each call to the encoder, to NewSealer and to Emit. It does this with a small budget and with a large one, and with a disk that stays full. It found two faults, which are now fixed (design.md §8), each with a test that fails without the fix:

    • When the encoder failed on a chunk that was not the last to return, the chunks after it waited for it for ever. The member never became complete, so the build left it out with no error, and its spill file and its budget stayed held. No codec of eictar gives such an error now: zstd and s2 give none, and deflate and xz fail on every chunk or on none.
    • After the build stopped, a member that the reader read at that time could still submit its chunks, because select chooses at random. Its AddFile then gave no error, and it was emitted after the failure. Finish gave the error, so no archive was wrong.

  • In extraction, each operation on the destination goes through a destDir (dest.go): in production an os.Root, so that no name leads out of the destination. The calls of meta on a descriptor (a pipe, a device, the times of a link, an extended attribute) go through it too. TestExtractFaultsAreNeverSilent makes each of about 100 operations fail in turn: into an empty directory, over the tree, and with --keep-going. These rules apply:

    • An extraction that reports success, with no failed member, had no fault, apart from the close of a handle that wrote nothing.
    • The error is the fault itself: an I/O error, not damage, and not an unsafe path.
    • No directory or file stays open, and no temporary file stays behind.

    It found one fault, which is now fixed: before a link, a pipe or a hardlink replaced a node, a failed lstat counted as “nothing there”. With the rule on the error, it also finds a fault that shows only later, as a link that was not made and then not found.

  • The walk of a create, an append, a --diff and the training of a dictionary goes through a srcDir (src.go): in production an os.Root, so that each entry is found through the directory that holds it (doc/Security_Audit.md, finding 11). The reads of each file, of its holes and of its extended attributes go through it too. TestCreateFaultsAreNeverSilent makes each operation fail in turn, for a create, with --keep-going, -h and --one-file-system, for an append, with --keep-going and with -u by digest, and for a --diff, with and without --keep-going. The rules are those of extraction, and one more: without --keep-going, a fault stops the run with its error. A --diff that finds a difference has not failed, so a fault must not show as one. The test found four faults, which are now fixed:

    • The stat that gives --one-file-system its device ignored a failure. The device was then 0, each directory was on another file system, and the archive was empty, with no error. Now the walk makes the stat only for --one-file-system, and a failure stops it.
    • A requested path whose parent did not open was walked by its path, for any error. That is for a parent that the user cannot list: now only a permission error does it.
    • Each error that opened a directory of the walk was “changed after the walk found it”. A fault of the disk is now itself, and only the errors of a change (gone, not a directory, a link) say that.
    • --diff did not check a hardlink whose target did not lstat, for any error, and found no difference. Only a target that is gone is not checked now: the walk reports it as missing. The first form of this fix counted the failure and gave no error, because the check of hardlinks comes after the run reads its first error. The rule on --keep-going found that before the fix was committed.

Part 2, power loss, is done. crash_test.go puts a model of the disk behind the same fileSystem. The operations reach the disk as in production. Beside them, the model keeps the content of each file at its last fsync, each write since then, and the names of the directory at its last directory fsync. After each change, it records what the path of the archive can hold if the power fails then:

  • the names of the last directory fsync, or the current names;
  • for the file at that name: its content at its last fsync; its current content; the content at its last fsync with half of what came after (a torn write); or its current content with one write since the last fsync lost (writes that reach the disk out of order).

TestPowerLossLeavesTheOldOrTheNewArchive runs the operations of part 1, and checks each state that the model recorded. These rules apply:

  • The archive holds its old state or its new state.
  • An operation that writes in place (append, delete, repair) can need --repair to give one of them back. An operation that commits with a rename (create, compact, recompress, a change of passphrase) must never need it.
  • When the operation has reported success, the state that the fsync calls put on the disk is the new one.

No operation broke a rule. Five faults put in on purpose were each found: no fsync of a new archive before its rename, no fsync of the directory after the rename, no fsync of a compacted archive, no fsync of the index before the trailer, and no fsync after repair cuts the file. The fourth one needs the model of lost writes. The index and the trailer reach the disk, but a write of a blob before them does not, so the archive opens as the new generation, and its members fail their digest.

The model takes a file system that keeps a rename in order with the other changes to the directory, and that does not change bytes that no write touched. It does not model a disk that lies about fsync.

Part 3, faults in the stress tester, is done. A file of archive that is built only with -tags faultinject (faultinject.go) puts a layer on the same fileSystem. EICTAR_FAULT=KIND:N makes the Nth operation of a kind fail, and a line on stderr says that it happened. A release binary does not have the file. make stress-build builds .build/eictar-faults with it, and the stress tester runs a change of the archive with it at random (§4). Thus the faults meet the random trees, codecs, dictionaries and histories of the stress tester, which the unit tests of part 1 do not. A run of five minutes made 167 changes with a fault, and in 33 of them the fault happened and the command failed. Each one exited with 4, and left the old state or the new one, with no file beside the archive. No rule broke. make vet checks the file with the tag, so that it cannot stop compiling.

With this, step 3 is done.

Step 4. More fuzzing. A fuzz target opens, lists, verifies and extracts changed copies of the golden archives into a temporary root. Each run must end with exit 3, or with the exact content, and never with a panic or a write outside the root. More targets cover the chunk opener, the configuration parser, the compression spec, and the pattern rules against a simple reference matcher. Before a release, each target runs for hours, and the corpus is kept.

Done. make fuzz runs twelve targets (FUZZ_TARGETS). The six new ones:

  • FuzzArchive (archive) changes the bytes of a golden archive, then lists, verifies and extracts it into a temporary root. Each operation ends with an error that gives exit 3, or with success. A successful extraction gives exactly the content of a generation of a golden archive: a cut at the end of a generation makes an older archive that is valid. The target finds the content of each such cut before it starts. Verify and extraction agree. Nothing is written in the temporary directory outside the root. The target takes bytes alone, because the fuzzer changes one golden archive into another, and the header of a plain archive is not authenticated. Its first run found that fault in the target, not in eictar. A changed crypto header can ask for 4 GiB for the key derivation, so the target lets the machine have 32 MiB (kdfMemory). The derivation is then refused above 16 MiB.
  • FuzzChunkOpen and FuzzIndexAndDictOpen (crypt): a sealed chunk, index or dictionary opens only if the sealer makes the same bytes from its plaintext, in its place. It does not open at another index, with the other final flag, in another member, or for another generation or id.
  • FuzzMatch (fsutil) compares Match with a matcher that follows the four rules of design.md §10.11 and has a glob of its own, which fills a table and does not backtrack. The patterns are of a, b, *, ? and /. With one rule taken out of Match, it finds a difference in less than a second.
  • FuzzCompressSpec (cli): a spec that parses has a name, and no empty key or value, and its String parses back to the same spec.
  • FuzzConfigFile (cli): any content of a configuration file gives a usage error, an error of the read for a line that is too long, or settings that --show-config shows.

In their first runs, FuzzArchive ran 5 minutes (about one million inputs), and FuzzMatch one minute (27 million). No fault of eictar came out. Go keeps the corpus in .gobuildcache/fuzz. The runs of hours before a release are for step 6.

Step 5. Models of the protocols. TLA+ models check three protocols, where faults of order and of timing hide:

  • the commit of a generation, and --repair (design.md §9.1, §9.5)
  • the lock, and the check that the path still names the locked file (design.md §9.6)
  • the rules of the memory budget against a deadlock (design.md §8.1)

The two hangs that the tests found were both in the memory budget.

Done. make tla checks four models in spec/ with TLC, the model checker of TLA+. TLC needs Java and tla2tools.jar (from the releases of github.com/tlaplus/tlaplus) in the root of the project. Git does not keep the jar, and the CI does not run the models. Each model has configurations that take out one guarantee of the program, and TLC must find the fault in each. Thus a model that cannot see a fault makes make tla fail.

  • Commit.tla: an append, an update or a delete (design.md §9.1), and the cut-back after an error. The disk keeps each write and truncate in a cache until an fsync. At a power failure, any subset of the cached operations is on the disk, in order, and a write can be torn. In each state, after a power failure, the archive gives the old generation or the new one, at worst after --repair. A success is durable. An error leaves the old archive when the truncate worked. TLC finds the fault when the fsync before the trailer, after the trailer, or after the cut-back is gone.
  • Replace.tla: a compact, a change of passphrase and a create, which rename a temporary file over the path (design.md §9.3, §9.7). The path gives the old archive or the complete new one, and a success is durable. Without the fsync of the new file, the path can name an incomplete archive. Without the fsync of the directory, a success is not durable. That is the case on Windows (design.md §15.1).
  • Writers.tla: appends, compacts and creates at the same time, with the lock and the check of the path (design.md §9.6). No append that reported success is lost, unless a create replaced the archive after it. TLC finds a lost append without the check of the path, and when a compact reads its archive before it takes the lock, a fault that the code had before.
  • Budget.tla: the memory budget of a create (design.md §8.1). No state stops for ever, each member reaches the archive, the budget stays within its limit, and all of it comes back. TLC finds a deadlock without the spill before the wait (the hang that M8 fixed), with a spool that waits for budget, and with a budget of one chunk.

The models found one fault in the program. A create that found no archive at the path held no lock. A second create could then make an archive there, and an append could start on it. The first create renamed its own archive over it, and the append, which reported success, was lost. Now the rename of such a create fails when a file is at the path, and the create stops with exit 4 (design.md §9.6). TestCreateDoesNotReplaceAnArchiveThatAppeared fails without the fix.

The models also showed that design.md §9.1 listed one fsync more than the code makes: the blobs and the index have one fsync together. The text now follows the code.

The models have limits. A model is not the code, and only the tests check that the code does what its model does. The models are small: three members of three chunks, up to three workers, and up to six writers. They take a rename to be atomic, and a disk that does not lie about fsync, as the test of power loss does (step 3).

Step 6. The release gate. Before a tag, these must pass:

  • make check on each platform, as CI does
  • a run of the stress tester of at least 8 hours
  • each fuzz target for at least one hour
  • make mutate on each package, with no survivor that is not explained
  • govulncheck on the modules and the standard library
  • the TLA+ models

Done. make gate runs each step that one machine can run, in this order: make check, make tla, make vuln, make mutate on each package, make fuzz with one hour for each target, and make stress for 8 hours. The CI workflow gives make check on the other platforms (design.md §12.3). The quick steps come first, so that a fault in them stops the gate before the long steps start. The gate stops at the first step that fails, because a fix makes a new commit, and the gate must run again on that commit.

The gate runs on a git worktree of the commit, in .tmp/gate/. Thus the result belongs to that commit, and not to the changes in the working tree, and work can continue while the gate runs. Also, a mutant can write files in the directory of its package, where go test runs it. In the gate, these files stay in the worktree, which the gate removes. The worktree uses the caches of the project, so the fuzz corpus grows from one gate to the next. The gate writes the output of each step to a log in .build/gate/SHA/, and a record with the commit, the toolchain, and the result and time of each step. The last line of the record is PASS only when every step ran and passed. The release steps of design.md §12.3 ask for this line. When a step fails, the worktree stays for the examination. For example, it holds the input of a fuzz target that failed, in testdata/fuzz.

make vuln runs govulncheck (golang.org/x/vuln, at a fixed version). It finds only the vulnerabilities that the code calls, so a vulnerability in a function that eictar does not use does not stop a release. The scan uses the toolchain that builds, because the standard library is part of the binary. The release workflow runs make vuln too, with the toolchain that builds the release binaries.

The scan knows only the entries of the Go vulnerability database. An advisory that a module publishes on GitHub can come days before its entry, or with no entry. GHSA-fpmh-frq8-7rj8, a panic of the zstd decoder of klauspost/compress v1.20.1 and earlier on a crafted frame, had no entry when the gate passed make vuln. Thus a release also needs a read of the advisories and the release notes of each module (design.md §12.3, step 1).

The first run of the gate found a vulnerability. GO-2026-6604 lets os.Root.MkdirAll follow a junction out of the root on Windows. An extraction uses os.Root to keep each member in the destination (design.md §7.6). Go 1.27.2 fixes it. The toolchain of the development machine was 1.27.1, so the gate stopped at make vuln. The release workflow takes the newest patch release of the version in go.mod (check-latest of setup-go), so a release built after Go 1.27.2 has the fix. Without check-latest, an older 1.27.x in the cache of the runner satisfies go.mod.

The first run also found a mutant in pipeline that the tests found only by chance of timing. A member is complete when the reader drops its claim and every chunk is in the spool. Either one can come last, but in a build the last chunk usually comes after the reader. Thus a fault in the check of the reader showed in the runs of step 1, and not in this run. TestMemberCompletesInEitherOrder now gives both orders.

In archive, the run found two more gaps:

  • The rename of step 5, which does not replace a file, had one survivor and four mutants that no test ran. A check after link(2) did the same as the check that follows it, so it is gone. The path for a file system with no hard links had no test. TestRenameNew now gives both kinds of file system: the name is free, the name is in use, and the check fails.
  • Two entries of the accepted list in capture.go said that a file with one name never has the identity of another file. That is false under -h: a symbolic link and its target are one file with one name. A test of the dry run from step 1 finds both mutants, so the entries are gone. Thus the rule that an entry must stay true worked.

The step took 3 hours and 21 minutes, of which archive took 3 hours.

The work on the gate also found that the operational tests left the binary that they built in .tmp/, which no one clears. Each mutant of cli runs them, so the runs of step 1 left 2,700 binaries, or 23 GB. A TestMain now removes the binary after the tests (RemoveBinary). A test that stops at its time limit still leaves its binary. In the gate, the worktree goes with it.

The second run of the gate, on 2026-10-17, passed check, tla, vuln and mutate (3 hours and 35 minutes). Then FuzzArchive found a zstd frame that eictar refused and the second reader read, after 52 minutes of the fuzz step. The cause was a gap in doc/format.md (step 2). The input is in src/internal/archive/testdata/fuzz/FuzzArchive, so each test run tries it again.

A CI run on Linux stopped after 30 minutes in TestPromptReadFails, and the next run passed. A goroutine dump showed the prompt in a loop of reads. After a terminal hangs up, each read gives 0 bytes and no error, and term.ReadPassword reads again for ever. The test closes the terminal while the prompt waits, and the fault showed only when the close came between the set of the terminal and the first read. A loop of 3,000 runs under -race stopped in the same way in 4 minutes. TestPromptAfterAHangup now gives the hangup before the read every time, and eictar reads the line itself (design.md §10.3). The mutation step found three survivors in the new code: the settings of the terminal, and an error of each call that reads or sets them. TestReadPasswordSetsTheTerminal now tests them. A terminal that cannot turn off the echo stops the prompt before it reads.

The third run of the gate, with klauspost/compress v1.20.2, stopped in mutate after 10 minutes. The recover in the training of a dictionary had a survivor. The trainer of v1.20.1 panicked on too little input, and TestTrainingFailsCleanly gave that input. The trainer of v1.20.2 returns an error for it, so no test made a panic. The recover stays, for a panic that is not known yet. TestTrainerPanicIsAnError replaces the trainer with one that panics. Thus an update of a module can take away what a test tests, and the mutation step finds it.

The fourth run of the gate passed check, tla, vuln and mutate (3 hours and 41 minutes). Then FuzzMatch stopped after 9 hours of the fuzz step, with a worker that did not reply. The fault was in the test, not in eictar. The glob of the reference tried each place for each *, and the pattern **************?b took 47 seconds. TestRefGlob gives the rules and a limit of 5 seconds for that pattern. The input is in src/internal/fsutil/testdata/fuzz/FuzzMatch.
